# ADR-0048: A deterministic policy decides whether a pull request may merge; a reviewing model can only withhold it

## Context and Problem Statement

Every commit to this repository is generated by a model, and one person owns it. The `main`
ruleset requires one approving review. GitHub does not let an author approve their own pull
request, so the only way anything can merge is the organization-admin bypass. As a result,
the review requirement exists on paper and nothing enforces it.

Dependabot now proposes updates to every pinned dependency (#88). An update is small, frequent
and mostly routine, and it is exactly where supply-chain attacks land. The compromised npm
releases of 2025 and 2026 all arrived as patch or minor versions, inside the days before any
advisory existed. Semver doesn't say how risky an update is: Dependabot labels Python 3.12 →
3.14 a *minor* update, and gives Postgres's `18.6-alpine` tag no update type at all.

A model can now review a diff against `CLAUDE.md` well enough to be useful. It can also be
talked into things. The text it reads is written by whoever wrote the pull request, including
the title, body, commit messages, and release notes it fetches from a third party. In a
reviewer that can approve and merge, prompt injection is a merge path.

Inference costs money on every run. A reviewer that runs on each push reviews work that isn't
finished, and it spends the most on the pull requests that change the most while they are
still changing.

## Decision Drivers

* **Nothing a pull request says can make it mergeable.** Whatever decides eligibility has to be
  immune to the text it is judging.
* **The paths `CLAUDE.md` reserves for human review stay reserved.** That means booking
  semantics, the write path, auth, migrations, CI, infrastructure and the constitution itself,
  and the platform should enforce it rather than the reviewer.
* **As little human attention as the risk allows.** One person's attention is the scarcest
  resource the project has.
* **Inference is spent on finished work only**, and never twice on the same commit.
* **No new runtime dependency and no second rulebook.** The rules are `CLAUDE.md` and these
  records (ADR-0001).

## Considered Options

* A deterministic policy decides eligibility; a model reviews on request and can only withhold
* Merge Dependabot updates on green CI, with no model
* A model reviewer that approves and merges on its own judgment, on every push
* Anthropic's managed Code Review
* A person reviews everything

## Decision Outcome

Chosen option: "A deterministic policy decides eligibility; a model reviews on request and can
only withhold". A pull request merges without a person only when a policy that reads no prose
allows it, the reviewer approves it, and CI is green. The reviewer runs when asked, never on a
push.

The policy's parts:

* **Protected paths.** A path listed in `.github/CODEOWNERS` is reviewed by a person. The
  ruleset requires a code owner's approval, so the reviewing app's approval satisfies the rule
  only for a pull request that touches none of those paths. GitHub enforces this boundary, not
  the reviewer.
* **Tiers.** `scripts/review_policy.py` puts every pull request in one of two tiers: `auto`
  may merge on the reviewer's approval, `human` needs a person.

  | Change | Tier |
  |---|---|
  | Touches a code-owned path | human |
  | `pyproject.toml` changes anything other than versions, or the runtime closure (`uv export --no-dev`) gains a package | human |
  | Dependabot `uv`, patch or minor | auto |
  | Dependabot `docker` (the Python and uv images), patch only | auto |
  | Dependabot `github_actions` or `docker_compose` (Postgres, Keycloak), any size | human |
  | Any Dependabot update with no update type, or a major | human |
  | Any other bot | human |
  | A person's pull request touching none of the above | auto |

* **Triggers.** The reviewer runs when:
  * someone adds the `merge` label, which is the final check before merging (`review:deep`
    uses the larger model);
  * the weekly sweep finds an open Dependabot pull request with no verdict at its head commit;
  * someone dispatches it by hand.

  It never runs on open or push. A head commit that already carries a verdict is not
  reviewed again.
* **Verdicts.** The verdict is `approve`, `changes` or `escalate`, with findings graded Important
  or Nit (`REVIEW.md`).
  * An approval with no Important finding, in the `auto` tier, becomes the app's approval
    plus GitHub auto-merge. The merge still waits for **All gates**.
  * On a person's pull request, Important findings start a fix round, at most two. Dependabot's
    are never fixed.
  * Everything else is labeled `needs-human`.
* **Supply chain.** Dependabot proposes updates monthly, with a cooldown of 7 days, or 30 for a
  major `uv` update. `uv` is the only ecosystem here whose cooldown Dependabot sizes by semver,
  and the other ecosystems' majors go to a person anyway.
* **Trust.** Both triggers run the workflow and the policy from `main`, and check out the pull
  request only as data. Forks are refused. The only credential that can write is minted after
  every model step has finished.

### Consequences

* Good, because prompt injection can't widen what merges. At worst it withholds an approval,
  which fails safe.
* Good, because the reserved paths are enforced by GitHub rather than by instructions, and a
  manipulated reviewer can't merge a ledger change.
* Good, because routine updates stop needing a person: grouped `uv` updates and image patches
  merge on their own.
* Good, because cost is bounded by requests rather than pushes. It is at most five sweep
  reviews a week on the smaller model, plus one review per `merge` label.
* Bad, because updates to Actions, Postgres and Keycloak always wait for a person. These are
  the cases where a green CI proves least.
* Bad, because the author can't approve their own pull request, so a person's change to a
  protected path still merges through the admin bypass. The bypass becomes a deliberate act
  instead of the only one.
* Bad, because the reviewing app is a credential that can approve, merge and push. Its key
  is a secret to keep, and its permissions are part of the boundary.
* Neutral, because `REVIEW_MODE` (`shadow` or `enforce`) switches every write except the review
  comment. That makes the reviewer's calls observable before they take effect.

### Confirmation

* The ruleset requires code-owner review, and `.github/CODEOWNERS` lists the protected paths.
  GitHub enforces both.
* `tests/test_review_policy.py` holds the tier table as cases. They include the actual shapes
  of the first Dependabot pull requests, and the expected values come from this record.
* `.github/workflows/review.yml` runs the policy from a checkout of `main`. Because
  `/.github/` and `/scripts/` are code-owned, changing the workflow or the policy needs a
  person.
* Nothing checks the quality of the reviewer's judgment. That is by construction: its
  judgment is never what grants a merge.

## Pros and Cons of the Options

### A deterministic policy decides eligibility; a model reviews on request and can only withhold

* Good, because each part does what it is reliable at. Rules that must hold are checked by
  code and by the platform. Judgment that can't be written as rules comes from the model,
  and it can only subtract.
* Good, because the policy is short, standard-library only, and tested against real inputs.
* Bad, because it is two mechanisms where one might seem enough, and the tier table has to be
  kept in step with `CLAUDE.md` whenever a reserved area moves.

### Merge Dependabot updates on green CI, with no model

This is GitHub's documented pattern (`dependabot/fetch-metadata` plus `gh pr merge --auto`)
and costs nothing.

* Good, because it has no inference cost and nothing to inject into.
* Bad, because CI proves the code still passes, not that the update is benign. A compromised
  patch release passes CI by design. Nobody reads the changelog, so a deprecation the code
  relies on or a relicensing goes unnoticed until it breaks.
* Bad, because it covers none of the person-authored pull requests, which are where
  `CLAUDE.md`'s unchecked rules actually get broken.

### A model reviewer that approves and merges on its own judgment, on every push

This is the most hands-off design, and it is how many teams run review bots.

* Good, because nobody ever has to ask for a review.
* Bad, because eligibility then depends on text the pull request controls. One persuasive
  release note can turn into a merge, and no instruction in a prompt can close that. Anthropic
  hit the same failure in its own pipeline: an agent asked another agent to deploy, and only a
  hard gate stopped it.
* Bad, because reviewing on every push spends the most on unfinished work. The owner has
  ruled that cost out.

### Anthropic's managed Code Review

A multi-agent reviewer hosted by Anthropic. It verifies its findings, reads `CLAUDE.md` and
`REVIEW.md`, and posts a check run.

* Good, because it is deeper than one agent, with verification built in, and nothing to
  maintain.
* Bad, because it requires a Team or Enterprise plan and bills about $15–25 per review.
* Bad, because its check run always finishes neutral, so it can't gate a merge without a
  second workflow parsing its output. Gating is the part this decision needs.

### A person reviews everything

This is what the ruleset already says.

* Good, because it is the strongest review available.
* Bad, because the one person who could review is the author, GitHub forbids self-approval,
  and every pull request so far has merged through the bypass. A requirement that can't be
  met doesn't control anything.

## More Information

**Follow-on obligations.**

* When `CLAUDE.md` reserves a new area for human review, `.github/CODEOWNERS` gains its path in
  the same change.
* The reviewing app is a GitHub App installed on this repository alone, with Contents,
  Pull requests, Issues and Actions write permissions. It has no Workflows permission, so a
  fix round can't push a workflow change even if it tries.
* The review workflow stays out of `ci.yml`, whose portability job must remain free of
  credentials (ADR-0004).
* `CLAUDE.md` states how merging works: sessions add the label instead of merging.

**Reversal cost.** Low. Deleting the workflow, the policy and the ruleset's code-owner
requirement restores the previous state. Nothing in the product depends on any of it.

The procedure the reviewer follows is `REVIEW.md`. It holds no rules.

## Revisit when

* A second person gains write access. Self-approval then stops being the constraint, and
  person-to-person review of the protected paths becomes possible.
* The reviewer approves something that later has to be reverted, or it escalates more than
  about half of the `auto`-tier pull requests it sees. Either one means its calibration or the
  tier table is wrong.
* GitHub lets a check run gate merges on its findings, or managed review supports a blocking
  conclusion. The second workflow this design needs would then be unnecessary.
